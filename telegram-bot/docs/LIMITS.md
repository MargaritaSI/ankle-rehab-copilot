## 1. Объём пушей и лимиты

**Пуши одного юзера в сутки** (дефолт: окно 08:00–23:30, интервал 60 мин):
утро 1 + микро-пуши 15 (09:00…23:00) + вечер/дневник 1 + food-push ≤1 (17–19 ч) + walk ≤2 = **~18/день**.
Минимальный интервал (15 мин, `handlers_extra.ts` setIntervalSave) = ~62 микро → **~65/день** на юзера.
**Группа**: окно 09:00 + 20:00 + тарелка 17:00 = 3 поста, закрытие = 2 edit + 2 editMarkup, воскресенье +1 → **~7 вызовов/день**
(+2 вызова на каждый тап участника: answerCallbackQuery + editMessageText).
30 юзеров + 2 группы: **540 пушей/день** (дефолт), до **~1950** (интервал 15) + ~14 групповых вызовов.

| Лимит | Оценка для 30 юзеров / 2 групп | Статус |
|---|---|---|
| Workers 100k req/день | 96 cron + ~1.5k webhook ≈ **<2k**. Исходящие fetch запросами не считаются | OK (запас ×50) |
| D1 5M reads/день | `usersForTick` 30 строк × 96 ≈ 3k + food-цикл ~1k + KB-поиск 438 строк × вопрос. **<50k** | OK |
| D1 100k writes/день | 540 пушей × 2 UPDATE ≈ 1.1k; при интервале 15 ≈ 4k. **<5k** | OK |
| Telegram 30 msg/с | тик шлёт последовательно (~5 msg/с) | OK |
| Telegram 1 msg/с на чат | у юзера ≤2 сообщения за тик (micro + food) с паузой в десятки мс; burst Telegram терпит, 429 теперь ретраится 1 раз (Part A) | OK |
| Telegram 20 msg/мин на группу | 3 поста/день; риск только при >20 тапов/мин (каждый тап = editMessageText) — 429 ретраится, иначе счётчик на посте отстаёт, данные в D1 целы | риск низкий |
| **Subrequests 50/вызов (free)** — D1-запросы и fetch считаются **вместе** | см. ниже | **ЛОМАЕТСЯ** |
| CPU 10 мс/вызов | тик — JS почти нет, ожидание I/O не считается; **`/leg`: `searchKb` парсит `JSON.parse` 438 эмбеддингов по 1024 float (~9 МБ)** (`leg_rag.ts:65`) — десятки мс CPU | **риск/ломается уже сейчас** |
| waitUntil 30 с (webhook) | `/leg`: `GEN_TIMEOUT_MS = 50_000` (`ai.ts:26`) > 30 с → ответ и сообщение об ошибке могут не отправиться | **риск** |

### Subrequests за один 15-минутный тик (потолок 50, считаются D1 + Telegram + AI)
Стоимость на юзера: утро = needsLegNudge 1 + send 1 + setLastMorning 1 + markReminded 1 = **4**; вечер = **3** (+1 в вс);
микро-пуш = send + markReminded = **2**; food-цикл (17:00–19:00) на КАЖДОГО юзера КАЖДЫЙ тик: `ensureUser` = **2** (INSERT OR IGNORE + SELECT,
`scheduler.ts:233` — лишний, `baseUser` уже полная строка) + при отсутствии push за день `foodToday` 1 + `lastFoodEntryAt` 1 + send 1 + markFoodPushed 1 = **6–8**.
Фикс. накладные: usersForTick 1, usersWalking 1, listEnabledGroups 1, на группу 2 + (3 открытие + 4 закрытие).

| Тик | Формула | Ломается при |
|---|---|---|
| 08:00 (утро, все в Амстердаме) | 1 + 4n | **n ≈ 12 юзеров** |
| :00 (микро-пуш, интервал 60) | 1 + 2n | **n ≈ 22** |
| 17:00 (food + микро) | 1 + (2 + 8)n | **n ≈ 5–6** |
| 17:15…19:00 (food уже отправлен) | 1 + 2n (только `ensureUser`) | **n ≈ 24 — даже когда пушей нет** |

Что происходит после 50-го: каждый следующий fetch/D1 бросает «Too many subrequests». `handleUser` ловится try/catch, но: (а) `safeSend`
глотает ошибку отправки, затем `setLastMorning/markReminded` тоже падают → утро/микро повторятся через тик (задержка 15 мин);
(б) если send прошёл (#50), а UPDATE (#51) нет → **дубль пуша** через тик; (в) `tickWalks` и **`tickGroups` стоят в конце**
(`scheduler.ts:160,167`) и остаются без квоты: слот открытия окна — ровно один тик (`handlers_group.ts:386`), а 09:00/17:00/20:00
совпадают с самыми тяжёлыми :00-тиками → **групповой пост за день теряется безвозвратно** (claim даже не делается).
Фикс: (1) `tickGroups`/`tickWalks` ВЫНЕСТИ ПЕРЕД циклом юзеров; (2) убрать `ensureUser` из food-цикла, пре-фильтр по
`last_food_push_at === today` до запросов, один агрегирующий запрос `GROUP BY tg_id` вместо двух на юзера; (3) UPDATE-ы
собирать и писать одним `db.batch()` (1 subrequest); (4) лимит ~20 юзеров на тик (остальные — следующим, состояние уже в БД);
(5) при росте — Workers Paid ($5, 1000 subrequests) или Queues fan-out. Поиск по `/leg`: хранить эмбеддинги как Float32-BLOB
(4 КБ вместо 20 КБ JSON) либо Vectorize.
Ещё: `/admin/ingest` — на 20 чанков 2 subrequest (embed + batch) → **>~480 чанков в одном POST упрутся в 50** (KB сейчас ~438 — впритык).
Мелочь: `foodToday` считает «сегодня» по UTC (`db.ts` ~424), для зон с большим отрицательным смещением даёт ложный «мало белка».

## 2. Где ответ может пропасть

| Путь | Статус | Фикс одной строкой |
|---|---|---|
| sendMessage 400 «message is too long» | **исправлено** (нарезка ≤3900, `telegram.ts`) | — |
| editMessageText > 4096 | **исправлено** (обрезка 4000 + «…», теги закрываются) | — |
| HTML не разобрался (400 can't parse entities): `handlers_leg` режет по 3800 и может разорвать `<b>`; пользовательский текст в `<b>` | **исправлено** (повтор простым текстом) | — |
| 429 | **исправлено частично** (1 ретрай при `retry_after` ≤5 с; иначе ошибка → глотается `safeSend`) | `safeSend` возвращает boolean; не ставить `markReminded`, если не ушло |
| Зависший fetch к Telegram | **исправлено** (8 с таймаут) | — |
| `safeSend` (`scheduler.ts:106`, дубль в `handlers_diary.ts`) глотает любую ошибку, а `setLastMorning/Evening/markReminded` ставятся ВСЕГДА | осталось: сбой отправки = «утро/вечер сегодня уже было» | возвращать успех и метить только при успехе |
| 403 в личке (юзер заблокировал бота): `reminders_on` остаётся 1 → каждый тик тратит 2–3 subrequest впустую | осталось | на 403 → `updateUser(reminders_on=0)` |
| 403 в группе | OK (`handleSendError` отключает группу) | — |
| `ctx.waitUntil` 30 с на webhook: `/leg` генерация до 50 с (`ai.ts:26`) | осталось | `GEN_TIMEOUT_MS` ≤ 22 с, `max_tokens` ↓, сообщение «не успела» |
| Исключение посреди цикла `tickMinute` | OK по логике (try/catch на юзера), но при исчерпании subrequests падают ВСЕ дальше | см. п.1 (порядок, batch, лимит) |
| Группа: `openWindow` упал не по 403 → `releaseGroupWindow`, но слот = один тик (`handlers_group.ts:386`) → повтора не будет | осталось | открывать в `[m, m+30)` — claim идемпотентен (UNIQUE) |
| Webhook отвечает 200 до обработки (`index.ts:90`), ошибка handler'а только в логе | by design | при желании — `sendMessage` «что-то пошло не так» в catch |

## 3. Безопасность

| Пункт | |
|---|---|
| Webhook secret: `X-Telegram-Bot-Api-Secret-Token !== env.WEBHOOK_SECRET` → 403 (`index.ts:78-80`); если секрет не задан — заголовок `null !== undefined`, всё равно 403 | ✅ (сравнение не constant-time — риск теоретический) |
| `/admin/*` (ingest, setcommands, leg): `ingestOk = !!INGEST_SECRET && header === secret` — fail-closed (`index.ts:21-23,27,46,59`); секрет только в заголовке, не в query | ✅ |
| `/admin/ingest` без лимита размера тела/числа чанков; `reset` стирает KB | ⚠️ (за секретом; упирается в 50 subrequests) |
| Экранирование: названия упражнений, имена в групповом счёте (`handlers_group.ts:107,140`), ответ `/leg` и источники (`handlers_leg.ts`) | ✅ |
| **Название цели (до 80 симв., `handlers_extra.ts:55`) вставляется в HTML без `escapeHtml`** (`handlers.ts:364,387,400,454`) | ⚠️ только в чате самого автора: сломает его сообщение (теперь plain-fallback), чужих затронуть не может |
| Callback-data: `groupCallback` (`Number.isInteger` + проверка chat_id окна), `diary:score` (1–5), `goal:del` (scope `tg_id`, `db.ts:356`), остальные — lookup по словарю/индексу, NaN → «не найдено» | ✅ |
| `/here` только для админа: `getChatMember` + анонимный админ `sender_chat.id === chat.id`; ошибка getChatMember → отказ (`handlers_group.ts:187-198,206`) | ✅ |
| FSM только в личке: `router.ts:197` (`chat.type === "private"`); команды личного потока отсекаются для групп `router.ts:146`; юзер заводится только из приватного чата (`router.ts:75`), в группе — `ensureUserQuiet` (reminders_on=0) | ✅ |
| Вызов модели из группы: `/leg`, `legPreset`, `legAskSave` отвечают `PRIVATE_ONLY` вне private | ✅ |
| Personal-чанки KB только владельцу (`OWNER_TG_ID`, `/admin/leg` без personal) | ✅ |
| Секреты в логах: `console.warn` пишет `TelegramError` (метод + описание), `AiError` (статус + 200 симв. тела), токен/ключ не попадают; токен — в URL исходящего fetch (так устроен Bot API) | ✅ (⚠️ не включать трассировку/логирование исходящих URL; `[observability] enabled = true` — только invocation-логи) |
| SQL: везде `?` + `.bind()`; единственная интерполяция — `updateUser` `SET ${setClause}` (`db.ts:113`), но имена колонок из белого списка `USER_FIELDS_ALLOWED` | ✅ |
| **Бот открыт любому пользователю Telegram**: нет allowlist/rate-limit; каждый `/start` = новый юзер с пушами (растёт нагрузка тика) и каждый `/leg` = вызов Nebius (грант) + эмбеддинг | ⚠️ главный незакрытый риск; нужен лимит `/leg` на юзера/сутки и/или allowlist |
| `.dev.vars` в `.gitignore`; в `wrangler.toml` нет секретов, только `DEFAULT_TZ` | ✅ |

## 4. Что сделать до деплоя (по убыванию риска)
1. `scheduler.ts`: `tickGroups`/`tickWalks` — ПЕРЕД циклом юзеров; не больше ~20 юзеров на тик; UPDATE-ы одним `db.batch()`.
2. Food-цикл: убрать `ensureUser`, пре-фильтр по `last_food_push_at`, один агрегирующий запрос на всех (иначе 17:00 ломается уже на 5–6 юзерах).
3. `safeSend` → boolean; `setLast*/markReminded` только при успехе; на 403 отключать `reminders_on` (нет дублей, нет потерь, нет мёртвых юзеров в тике).
4. `/leg`: `GEN_TIMEOUT_MS` ≤ 22 с (waitUntil 30 с), эмбеддинги в Float32-BLOB/Vectorize (CPU 10 мс), лимит вопросов на юзера в сутки.
5. Группа: окно открывать в `[m, m+30)`; `escapeHtml` для названий целей; ingest — пачками ≤ 400 чанков за запрос.
